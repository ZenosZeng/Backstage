# 开发与版本管理

[返回首页](../README.md) · [版本记录](changelog.md)

## 分支与PR

- `main` 是Linux生产分支，只接收经过检查的PR，不直接在其上开发、提交、推送或强推。
- 每项改动单独使用 `feat/描述`、`fix/描述`、`docs/描述`、`chore/描述` 或 `release/x.y.z`；不要求维护长期 `develop` 分支。
- 功能、修复、文档、依赖及版本号调整都通过PR；版本声明和对应功能或修复放在同一个PR。
- 开始前检查工作区和分支，保留已有改动。新分支通常基于最新 `origin/main`；已有未推送提交不得用reset或强推清除，应保留到待审PR中。

```bash
git fetch origin
git switch -c feat/short-description origin/main
```

提交采用中文Conventional Commits，例如 `feat: 增加项目导航`、`fix: 修复任务状态读取`。完成本地检查后，取得明确授权再推送分支、创建以 `main` 为目标的PR。PR中说明范围、版本、验证和兼容影响；合并以Squash为默认，标题作为中文提交摘要。

## 版本规则

| 级别 | 用途 | 示例 |
| --- | --- | --- |
| major | 不兼容改动，必须说明迁移和回退 | `1.x.x` → `2.0.0` |
| minor | 新增一组功能或显著增强 | `0.6.x` → `0.7.0` |
| patch | 兼容的bugfix、稳定性或安全修复 | `0.6.0` → `0.6.1` |

`0.x`阶段不兼容改动也须在PR和版本记录中明确标注，不能伪装成patch。只改文档或开发流程不强制升版，先记录在“未发布”，随下次版本归档。

应用版本以 `pixi.toml` 为准；记忆事件、飞书会话、配置等数据格式版本独立管理，不机械跟随应用版本。

README固定显示两项：

- 最新版本：实际最新应用版本，如 `v0.6.1`。
- 当前功能版本：该major/minor的功能起点，如 `v0.6.0`，下面保留这一版本的主要feature。

发布patch只更新“最新版本”及必要升级提示，不能用bugfix列表覆盖 `v0.6.0` 的feature。到 `v0.7.0` 或下一major时才更新功能摘要；此前特性和每次修复完整保存在 `docs/changelog.md`，按新到旧排列。版本记录不表示已经创建同名Git标签或GitHub Release。

## 合并检查

1. Linux环境运行 `pixi run -e dev test` 和 `pixi run -e dev lint`；现有 `tests` 工作流的 `unittest`、`tools` 检查均须通过。
2. 核对版本号、README功能摘要、版本记录和升级影响；文档或版本检查不应依赖真实S3、飞书凭据、生产日志或GPU。
3. 只暂存本次文件，不包含 `config.json`、`.share/`、`.local/`、完整聊天、真实记忆或凭据。
4. 保持Linux公共实现；Windows补丁文件可经PR维护，但不得把本机应用补丁后的专用源码误提交。详见 [补丁说明](../patches/README.md)。
5. 检查通过并获得合并授权后才合入 `main`。单人仓库也保留PR记录，不要求作者自审批准；多人协作可要求独立review。

要在GitHub服务端强制执行，须另行启用 `main` 分支保护或Ruleset：要求PR及检查通过、禁止强推和删除，并核对管理员绕过权限。文档和PR模板不能代替服务端保护；提交或合并本规范不自动修改GitHub设置。

## 发布边界

- 合并不等于发布。软件标签 `vX.Y.Z` 和Release只能在单独授权后指向已合入、验收通过的 `main` 提交；记录实际标签、提交和发布日期。
- 本地改文档、测试或升版本，不代表已推送、合并或上线。未经验证不得写“生产已更新”。
- 代码合并不自动部署 `.agents`、同步S3或重启服务。这些操作与推送、创建或合并PR、打标签、发布分别需要明确授权，并遵守本机的LOCAL-ONLY约束。
